2 · Exploratory data analysis

Three facts shape every downstream choice: the signal is extremely rare, launderers prefer one payment rail, and amounts are heavy-tailed so the median — not the mean — is the honest measure.

Class imbalance — the needle in the haystack

5,177 laundering transactions out of 5,078,345. Shown as 1,000 cells; about 1 in 981 is laundering.

Implication: a model that predicts "never launders" is 99.9% accurate and useless. RingSight is tuned for recall and explainability, and reports precision/recall honestly rather than headline accuracy.

Payment rail — the single strongest signal

Share of transactions on each rail: laundering vs. all traffic. Laundering is 86.6% ACH while ACH is only 11.8% of normal traffic.

3 · How the data is segregated

Two kinds of separation run before any model sees the data.

Sampling & labelling (from 5M rows to a workable graph)

5.08M transactions cannot be loaded or graphed interactively, and only 37% of laundering is USD→USD. The loader segregates in four steps, all seeded so the result is identical every run:

StepRuleEffect (IBM HI-Small)
Single currencykeep USD→USD only, so amounts are comparable5.08M → 1.67M
Keep all positivesevery laundering row is retained first+1,912 labelled
Seeded context + backgroundfill the rest with neighbours of flagged accounts, then random noise+28,088 normal
Canonical remap(bank, account) → ACC_0001…; sorted txns → T000001…30,000 txns / 29,459 accts

Legitimate vs. suspect (so good accounts aren't flagged)

In the synthetic source, payroll and merchant accounts fan out and fan in by design. They are tagged by account_type and excluded from the detectors, so legitimate hubs never raise an alert. Oversized hubs are also split out: a group larger than max_case_accounts or a payer with more than max_receivers counterparties is treated as an institution, not a ring. Every threshold lives in config/rules.yaml.

Deterministic vs. generative

The last separation is architectural and the reason the output is defensible: detection and validation are rule-based and reproducible; only the SAR wording is LLM. The machine's judgement and the machine's prose are never entangled.

4 · Orchestration — coordinator & specialist agents

SAR drafting is a hub-and-spoke pipeline. A plain-Python coordinator (the orchestrator state machine) calls four single-purpose agents in order and owns the retry loop; the agents never call each other. Two are deterministic, two are the LLM.

deterministic (rule-based, reproducible) LLM (Groq gpt-oss) validator feedback loop
AgentDoesGuarantee
Evidence Builder detturns a case into ≤40 numbered evidence items (transactions, shared ids, metrics)only this compact pack is sent to the LLM — never raw data
Typology Agent LLMclassifies the laundering typology with a confidence and cited evidenceoutput parsed into a typed schema
Narrative Agent LLMdrafts the 5-section SAR; every sentence carries evidence idsrewrites only failing sentences on retry
Validator detchecks each sentence's amounts, dates, accounts and citations against the pack; bans speculationthe Grounding Score; it is the source of truth, not the model

The coordinator persists a versioned draft, a tamper-evident audit entry, and a decision_log row with confidence signals (evidence coverage, first-try pass rate, retries, fallback used) — the raw material for section 7.

7 · From reports to prevention

Today RingSight produces a report for a human to sign. Every run also quietly records the data needed to go further. Here is the honest current state and the path.

What already accumulates

  • Labelled alerts with the exact transactions behind them
  • Analyst verdicts (approve / reject + reason) in a tamper-evident log
  • Grounding scores and ConfidenceSignals per draft in decision_log
  • A deterministic, reproducible feature set per account and case

Fine-tune / train next

  • Learn a risk re-ranker from analyst verdicts to cut false positives (the IBM run shows the headroom: precision 0.54)
  • Distil the narrative model on approved SARs for a smaller, cheaper, house-style writer
  • Calibrate confidence so low-confidence drafts auto-escalate
  • Swap NetworkX → a GNN behind the same Alert interface

Batch report → live prevention

The detectors are pure functions over a graph window, so the same logic moves from "explain after the fact" to "act before settlement".

Prevention, not just paperwork: when a transaction entering the window would close a cycle or complete a structuring pattern, the system can hold it, step up authentication, or block it — then still emit the grounded SAR for the record. The report becomes the audit trail of an action, not the end of the process.

Current status: sections 1–6 are built and verified. Section 7's "next" items are the designed roadmap — the hooks (decision_log, the Alert interface, the gateway) exist today; the models and the streaming path do not yet.

Reliability & speed

  • Determinism: same seed → byte-identical case/evidence ids and a stable fingerprint (machine-checked).
  • Cached replay: a previously drafted SAR returns in ~0.0s, every agent call a cache hit — the live demo never waits on the network twice.
  • Graceful degradation: Groq 120b → Groq 20b → deterministic mock; the app never crashes on an LLM failure, and the mock still passes validation.
  • Guardrail proven: an injected false sentence citing a real id is caught every time (precision of the check, not luck).
